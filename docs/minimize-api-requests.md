# Экономия запросов к API

Внешний API имеет **дневной лимит** (ориентир: **~1500 запросов в день** на ключ/проект). Любой новый код должен **сначала** снижать число обращений к сети, а уже потом добавлять фичи.

## Обязательные практики

1. **Кэш с TTL**  
   Повторяющиеся данные (таблица, турнир, матчи за день, состав команд) — только через общий слой с кэшем и осмысленным временем жизни. Не дублировать сырой `axios.get` в компонентах без кэша.

2. **Дедуп параллельных одинаковых запросов**  
   Если два вызова с одним и тем же ключом кэша стартуют одновременно — должен уйти **один** HTTP-запрос (общий `Promise` / in-flight map).

3. **Один источник правды**  
   Не дергать одни и те же эндпоинты из нескольких мест без необходимости. Предпочитать: один запрос → прокинуть данные / React Query / контекст / уже закэшированный `getX`.

4. **Polling только осознанно**  
   `setInterval` для обновления матчей — редко (например ≥60 с) и только при открытой вкладке; при уходе со страницы — `clearInterval`. Не опрашивать API «на всякий случай» каждые 5–10 с.

5. **Батчинг**  
   Если бэкенд умеет отдать несколько сущностей одним запросом — использовать это вместо N последовательных вызовов.

6. **Локальное хранилище как запасной кэш**  
   При 429 / offline отдавать последний успешный ответ из `localStorage`/memory cache, не бить API в цикле.

7. **Не сбрасывать кэш без причины**  
   Смена даты/команды — новый ключ кэша; не инвалидировать весь кэш приложения из UI.

## При реализации

- Любой новый вызов API — через `football-stats/src/services/api.js` (или аналог) с ключом и TTL.
- Перед добавлением `useEffect` с fetch — проверить: уже есть кэш? уже есть in-flight? нужен ли debounce?
- В PR/ревью явно отмечать оценку: «сколько запросов в минуту при типичном сценарии».
